# Citizen appearance and wardrobe contract

Citizen creation accepts seven curated cosmetic choices: six skin tones, three adult frames, five hairstyles, three hair colours, four clothing styles, six top colours and four trouser colours. The baseline palette is free. The server rejects missing fields, arbitrary colours, external assets/URLs, additional fields and unknown presets. Omitted appearance in older creation commands receives the same default. Age eligibility remains the existing adult confirmation; body frame does not establish or bypass account eligibility.

Creation provisions one saved version-1 profile alongside the citizen, starter benefits and command receipt. A repeated command returns its original receipt. Appearance does not affect allowance, needs, family assignment, votes, licences, wage checks or other eligibility. It creates no tradeable clothing entitlement or paid product.

After creation, the citizen may change these choices beside a placed wardrobe in the current usable home. The command checks location lease, current home layout version, wardrobe identity, real range and the intervening wall edge. A stored wardrobe, another object, stale layout, lost residence access or journey cannot authorize a change. Appearance has its own version to reject stale selections. Accepted changes record a Dress activity and another immutable receipt; retries cannot increment the version again. Current cosmetic choices remain personal through house/region changes.

The accessible form explains why saving is unavailable and offers an ordinary server-validated route to the wardrobe. Selecting the wardrobe focuses the appearance controls after confirmed arrival. Choices are submitted as IDs; passwords, arbitrary image uploads and browser authority are unrelated. The main 3D scene rebuilds and disposes the previous character geometry only when the confirmed appearance changes. It preserves position, facing and walking state, and keeps the existing reduced-motion path. Adult frames, hair and clothing differ geometrically rather than changing labels alone. Canvas uses the same confirmed colours/frame/hair/style; Low remains DOM accessible.

Citizen JSON and the existing private SQL citizen mirror persist the profile. Backup reconciliation and the additive deferred PostgreSQL constraint require curated choices and a matching creation/change receipt. The schema creates no public table or Data API access. Legacy citizens without a saved profile use the default appearance until an authorized wardrobe change.

Automated evidence covers atomic creation, invalid input, unchanged starter benefits, exact retry, distance/lease/layout/wardrobe permissions, blocked wall edges, storage, backup restoration, forged profile rejection, all hairstyle/outfit/frame geometry combinations, real HTTP/DOM creation/approach/save/response-loss retry, and PostgreSQL rollback/reopening/tamper rejection. GPU/device visuals, cultural and production-art acceptance, gender/facial/accessory customization, clothing manufacturing/markets and the full account/multiplayer requirements remain open. This contract is a completed local component, not approval of final Sims-quality art or completion of R003/R065.
